## How this work is done — follow this exactly

**Everything is proven on the real card, never on a simulation.** Adrian's card is
`lw-b0fe81f61b44`, usually at `192.168.18.70` (find it with
`dns-sd -t 2 -B _http._tcp` — it advertises as `Lightweaver-XXXX`). It is also on
USB at `/dev/cu.usbmodem*`. Tests passing is not evidence the flow works; driving
the browser against the live card is.

**Driving the browser.** Start the Studio dev server on port 9999
(`cd lightweaver && npm run dev -- --port 9999 --strictPort`). Chromium needs the
sandbox disabled to launch on this Mac (it dies with a mach-port error otherwise).
Use a long-lived Playwright process with an HTTP control port rather than one
script per step — a fresh `chromium.connect` per command creates a new browser
context each time, which silently loses `localStorage` and makes pairing look
broken when it is not. That mistake cost an hour; do not repeat it.

**Never edit source while Adrian is mid-walkthrough.** Vite hot-reloads the page,
which kills a running discovery session and leaves the strip fully lit. This
happened and was misread as a product bug.

**The three-stage pipeline Adrian wants:** Fable plans → DeepSeek executes →
Opus verifies.
- Plan with a Fable subagent. It cannot write files, so it returns the plan
  between `===== PLAN START =====` / `===== PLAN END =====` markers; save it
  yourself.
- **When saving a plan, do NOT use `html.unescape`.** It turns `&section` into
  `§` and corrupted a test URL. Replace only well-formed entities: `&amp;`
  `&lt;` `&gt;` `&quot;` `&#39;`.
- Execute with `opencode run -m opencode/deepseek-v4-flash-free --dir <repo> -f <plan>`,
  message on stdin. The free endpoint returns 503 "request queue is full" often —
  retry with backoff. Running more than ~5 in parallel causes "database is locked".
- Parallelise by file: two agents must never edit the same file.
- **Verify everything yourself.** DeepSeek has repeatedly claimed work it did not
  do, broken existing tests, and produced lowercase hex where the codebase uses
  uppercase. Every claim it makes must be checked against the tree and the tests.

**Firmware.** PlatformIO is installed. `cd firmware/lightweaver-controller && pio run`
then `pio run --target upload --upload-port /dev/cu.usbmodem*`. You may flash
without asking — Adrian is at the bench and has authorised it.

**Reporting to Adrian.** Short, plain language, no jargon, result first. He is
not reading code. When the physical strip needs looking at, ask one clear
question and stop.

## The rule Adrian set, which still holds

Two lists, worked strictly in order. **BROKEN** — anything that stops the setup
completing, strands the card, or records a wrong answer — gets fixed. **DEFERRED**
— anything that is merely slow, repetitive, or ambiguous — is not touched until
one complete loop has been walked successfully and its real steps are written
down. Then that captured process is what gets made easy.

The headline deferred problem, for context: setting up one card currently takes
